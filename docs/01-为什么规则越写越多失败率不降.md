# 为什么 agent 的规则越写越多，失败率不降

一个自我审计回路在真实工作机上跑了约两个月。下面是我数错过的三次，和最后剩下的那两个数。

所有数字都来自一台具体的机器：Windows 11 Insider + PowerShell 5.1 + 一个自研 agent harness（131 个会话 / 5966 步 / 151 次工具错误）。换个环境数字会变，**结论的形状不变**。

---

## 一、一个不动的数

一开始我盯的是「每千步错误数」。

它前两周很好看：写规则、加技能、加自检，从 90+ 掉到 40 左右。然后它就不动了：

```
第 1 周  37.8 / 千步
第 2 周  37.1 / 千步
第 3 周  37.9 / 千步
```

同一水平。而我的规则文件从 6 KB 涨到 21 KB，技能从 4 个涨到 30 多个。

有两种解释：要么规则没用，要么**这个数测的不是我以为的东西**。我花了很久才接受是后者。

那时候我犯的错，是把「错误事件数」当成「我犯错的程度」。这两件事之间隔了三个陷阱。

---

## 二、陷阱一：非零退出码不是失败

第一个陷阱最好笑。我统计的「错误」里，有 37% 根本不是错误：

- `rg TODO` 没匹配到 → 退出码 1，但「没匹配」就是我要的答案
- `Get-ChildItem ... | Select-Object -First 3` → 管道早停，退出码 1，命令其实干成了
- `node so.mjs` 判 FAIL → 检查器**正常跑完了**，它报告的问题另记在评审账本里
- `install.ps1 --dry-run` → 我本来就是问它会不会拒绝
- 进程被超时杀掉 → 不是命令写错

混在一起数，读数就随「今天查了多少次」而不是「今天错了几次」波动。

**改法**：六个桶，每个桶一条判据，判据必须能说出「为什么它不算我的失败」。

| 桶 | 含义 | 典型判据 |
|---|---|---|
| `real` | 真失败 | fail-closed：没命中任何规则就进这里 |
| `gate` | 检查器 / 守卫按设计拒绝 | 必须看到结论行，否则闸自己崩溃也会被当成「报告问题」静默排除 |
| `probe` | 探针 / dry-run | 命令本身就是验它会不会拒绝 |
| `idiom` | 命令干成了，退出码骗人 | 要求「有 stdout 且完全无 stderr」 |
| `killed` | 进程被终止 | 见退出码 -1 / 超时文案 |
| `env` | 换写法也过不去 | 链路、provider、配置 |

改完，真失败从 60.6 / 千步降到 38.3 / 千步——**什么都没修，只是不数错东西**。差值 22 点全是噪音。

这件事给的教训比数字重要：**同一个数，口径错了就是假的进步**。所以现在任何读数我都逼自己同时报两个口径（原始 / 真失败），差值本身是一个信息（噪音量）。

一处细节值得说：判断「无 stderr」时，如果脚本里任何一行出现过 `2>&1` / `2>$null`，这条判据就不成立——重定向之后我既看不到错误也无法证伪，「无 stderr」就失去证据力。这是评审连提三轮才补上的，第一轮只看末行，漏掉了 3 条 `2>$null` 的真样本。

---

## 三、陷阱二：能解释 ≠ 不是失败

第二个陷阱更隐蔽。当 `real` 桶里堆了 164 条时，我给它们加「根因」标签：参数名写错、正则被 shell 吃掉、编码乱码、依赖缺失……

然后我发现自己开始享受这个过程。每一条都有解释，每一条都可以说「哦这是那一类」。

危险在于：**能解释的东西会自动变成「不算失败」**。

所以定了一条硬规矩：**归因绝不降桶**。桶不变（真失败还是真失败），根因只回答一个问题——下一刀该砍哪里。

具体做法：
- 归因优先级与定义顺序**解耦**。新规则追加在数组末尾时会被更早的宽规则抢走：实测「漏必填参数」的 6 条全被 `/missing/` 吃掉；乱码行被 `/Add-Type/` 误判（长输出里本来就常出现这个词）。
- 顺序原则：命令名 + 字面证据最先 → 乱码（乱码时其他关键词都不可信）→ 工具层拒绝（命令根本没跑）→ 越具体越前。
- **规则表配合成样本自检**。一条写坏的正则不会报错，只会永远不命中——读数照样「正常」，归因却整体落到 `unclassified`。自检能在退化当场抓住它。

还有一条：`unclassified` 比例大**不等于**「长尾到头」。

---

## 四、陷阱三：频率不是复利

第三个陷阱是我最晚承认的。

即使口径全对，`38.3 / 千步` 这个数也不会动了。它测的是「我犯错多不多」，不是「这条路有没有在长东西」。

于是换了主指标：**被机制化（有证据压住）的失败类数**。

但这里有个自欺的捷径：自己在文档里手数「我修好了 8 类」——那等于自己给自己发合格证。所以把它变成可核的四条件：

```
① 产物在盘上                  —— 排除「我记得写过」
② 探针真跑过                  —— 文件存在不等于它会拦
③ 落地前 7 天该类真失败 ≥2 次  —— 没有前科就没有「压住」可言
④ 落地后 7 天里一次都没有      —— 后窗口没满只能算「观察中」
```

四条同时满足 = `holding`，进主指标。其余五类单列：

```
dead        产物不在盘 / 探针跑不过
declared    无可测根因 —— 建了工具 ≠ 压住了失败，永不进主指标
unproven    有根因无探针 / 前科不足 2 次
observing   后窗口还没满
leaking     落地后又来了 —— 没压住，给出最近一条的形态
```

`declared` 单列是这套东西的核心防线。没有它，「我建了 8 个工具」就能冒充「压住了 8 类失败」。

一个配套的量：**账本覆盖率**。第一周我报「278 步」，真实是 4091 步——账本只在我记得跑记账脚本的会话里记，覆盖率 7%。拿账本数当全量读数会低估一个量级。所以周报必须同时报覆盖率，它是「这个读数有多可信」的元数据。

## 五、三个判例

### 判例 1：23% 的失败来自同一个形状

164 条真失败里，38 条（23%）是同一类：

- 改文件之前没读过它
- 读到之后文件被自己另一条命令重写了
- 锚点文本太短，出现 2 次

解法不是写「优先用某工具」的纪律。纪律是对抗自己的注意力，而**注意力正是失败的那个东西**。

解法是把入口收窄：一个命令做完整回路——读 → 写前重读核对 → 改 → 回读 → 语法检查（坏则回滚）→ 退出码分明。三类从此结构上不可能发生（`src/edit-safe.mjs`）。

### 判例 2：纪律压不住的，机制压得住

同一类失败（写文件的三类）在换了入口之后仍然有 33 条 / 7 天。

原因不是我不听话，是**还有别的通道**：`terminal_send` 写文件走的是另一条路，`office_*` 也是，它们不经过我的入口。写再多纪律都压不住——纪律只能约束「我记得用它的那些时刻」。

解法是宿主层守卫：在 `edit` / `write` 覆盖已存在文件、`node -e "…"`、`$var:` 紧跟冒号、解析期语法错这几种**注定失败的命令形状**上，直接在执行前拒绝并给出替代写法。

纪律压不住，因为纪律要经过注意力；机制压得住，因为机制在执行路径上。

这条现在是那套系统里最硬的结论：**任何需要「记得」的规则，都是一条迟早会漏的规则。**

### 判例 3：「长尾到头」是我判错的

某个时刻我宣布：183 条真失败聚成 134 簇、最大簇 18 条、未归因 44%——长尾，到头了，不用再加规则。

两天后加了两条根因规则（Python traceback、PowerShell 原生错误），未归因从 144 降到 96。

错在**只看数字不看形态**。簇数、最大簇、未归因比例这三个数都能被「规则表写得差」伪造出来——规则宽了会把不同东西归成一簇，规则少了会让真问题落进 unclassified。

所以现在的规矩是：判「长尾」之前，先 `--cluster <根因>` 看它到底长什么样。

顺带值得写下的：同一条根因下的形态分布比根因总数有用得多。`ps-native-error` 一直是 top 3，但它的形态全是同一句——原生命令往 stderr 写了内容、被 PowerShell 包成 `NativeCommandError`，然后我去查 PS 语法。这种「形态单一但计数很高」的类别，一条待办就能消掉。

## 六、这套东西的三个前提

诚实起见，它不是通用方法论。

**1. 它需要你的失败被记录。**
输入是时间序列的失败事件。没有记录就没有前科，`mech.mjs` 是空转的。这也是它最脆弱的地方——它不测代码，它测「一段时间里发生了什么」。你得愿意把每次工具调用留下来。

**2. 它需要你愿意被自己的规则判 FAIL。**
自检加了「变异体必须被抓」这类断言之后，规则会开始拦我自己。最容易的应对是放宽规则——那就白做了。

**3. 它测不了「理解错了」。**
分类器覆盖不到的失败（需求理解错、方向选错）永远是 `declared`，刻意不假装能测。这类只能靠换先验（问人、叫异源模型复核），不能靠统计。

---

## 七、如果重来，我会少做哪些

- 少写规则条文。规则文本是每回合注入的成本，而它的作用是**提醒**，承担不了**执行**。能落到执行路径上的（守卫、单入口、模板），别写成纪律。
- 早一点做双口径。单口径的那两周，我把噪音当成了进步，还据此加了不该加的规则。
- 早一点做机制量表。没有它，我会一直用「我修好了几类」来自我说服，而那个数没有证据。
- 别在数字上宣布「到头了」，先看形态。
