# 输入格式

## events.jsonl —— 失败调用

一行一个**失败调用**（非零退出码、或工具层报错）。成功的调用不用记，只给总数。

```json
{"at":"2026-08-03T09:12:00Z","tool":"pwsh","cmd":"pwsh -File build.ps1","exit":1,"out":"","err":"Cannot find path 'C:\\out'"}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `at` | 是 | ISO 8601 时间。解析失败的整行会被计入 `badLines`，并在 `--strict` 下退出 3 |
| `tool` | 是 | 工具名（`pwsh` / `edit` / `bash` / `curl` / `web_fetch` …） |
| `cmd` | 是 | 传进去的命令 / 参数（规则会看它，例如 `--dry-run`、`Select-Object -First`） |
| `exit` | 建议 | 退出码。Windows 上被杀掉常见 `4294967295`（= -1） |
| `out` | 建议 | stdout。**注意**：若 harness 把 stderr 并进了 stdout（`2>&1`），「无 stderr」类判据会失去证据力 |
| `err` | 是 | stderr 或工具报错正文。多数规则都看它 |

`cmdText` 可选：多行脚本的完整原文（`cmd` 只放识别用的一行时），**最后一行**是 `ps-native-nomatch` / `ps-cmdlet-nomatch` 两条规则的判据依据。

**编码**：只有 UTF-8。若你的环境会把报错以 GBK 写出再按 UTF-8 解码（Windows PowerShell 5.1 常见），`err` 里会出现连片 `U+FFFD`——这些会被 `ps-gbk-garble` 抓住。那是「读数不可信」而不是外观问题：乱码时其他所有关键词规则都不可靠，所以归因顺序里它排第二。

## mechanisms.jsonl —— 机制账本

一行一项机制。

```json
{"id":"M01","ts":"2026-08-10T00:00:00Z","family":"报错文本乱码","kind":"tool",
 "artifact":"src/edit-safe.mjs","causes":["ps-gbk-garble"],
 "proof":[{"cmd":"node","args":["src/edit-safe.mjs","--selftest"]}],
 "note":"为什么它能压住"}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `id` | 是 | 唯一短名 |
| `ts` | 是 | 落地时刻。前 / 后窗口由它切开，写错就直接判歪 |
| `family` | 是 | 压住了哪类失败（人话） |
| `kind` | 是 | `tool` / `gate` / `rule` / `skill`。后两者天然拿不到「压住了」的证据，只会是 `declared` |
| `artifact` | 是 | 产物路径（相对当前工作目录或绝对路径）。必须存在，否则 `dead` |
| `causes` | 是 | 本仓库分类器的根因 id 数组。空数组 = 无可测前科。**元素必须是字符串**，且必须是 `src/classify.mjs` 里 `REAL_CAUSES` 的 id；写错一个字母会让机制永远匹配不到、安静地判成 `unproven`，所以账本校验会直接拒绝未知 id（`exit 1`）。改根因 id 属于破坏性变更，账本要同步改 |
| `proof` | 是 | `[{cmd,args,expectExit?}]`，会被**实际执行**。空数组且 causes 非空 → `unproven` |
| `note` | 建议 | 为什么它能压住，写给三个月后的自己 |

### 判定

```
产物不在盘            → dead       （记了但没落地）
探针跑不过            → dead       （落地了但坏了）
causes 为空           → declared   （这类失败测不了，永不进主指标）
有 causes 无 proof    → unproven   （没人跑过它，不配说压住了）
前窗口 < 2 次         → unproven   （一次可能是偶发）
后窗口未满            → observing  （还不到 7 天）
前有后无              → holding    ← 主指标只数这一个
前有后又来            → leaking    （没压住）
```

账本有任何一行不合格（缺字段、id 重复、ts 在未来），整个量表**报错退出**——跳过坏行会让生效数偏低，而错在账本上却表现为「机制没生效」，下一次就会去修本来没坏的机制。

## 怎么从自己的 harness 导出

以最常见的会话日志为例，写一个这样的转换脚本（伪代码）：

```js
for (const call of 会话里的每次工具调用) {
  if (call.exitCode === 0 && !call.error) continue;     // 成功的不记
  print(JSON.stringify({
    at: call.startedAt,
    tool: call.tool,
    cmd: call.args.map(String).join(' '),
    exit: call.exitCode ?? 0,
    out: call.stdout ?? '',
    err: call.error ?? call.stderr ?? '',
  }));
}
```

导出以后先跑一次 `classify --in ... --window 7`，看 6 个桶的比例是否讲得通：

- `idiom` 很高 → 你的失败定义太松，先把「查了没有」「管道早停」这类剔掉
- `env` 很高 → 是环境问题，换写法也过不去，别去改自己的命令
- `real` 的未归因比例 > 40% → 规则表还是别人的形状，先跑 `ledger --cluster unclassified` 看形态，再补规则

判「长尾到头」之前必须先看形态。曾经有一次我判「到头了」，后来加两条规则把未归因从 144 降到 96——**先看形态，再下结论**。
